这份文档不是一次性整理完成的产品，而是一套持续从子比主题、子主题和插件源码中提炼的公开资料。社区协作的目标，是让每一条结论都能被复核，让每一个错误都有清晰的追踪入口，并让经过验证的开发经验持续沉淀为可搜索、可引用的文档。

## 推荐协作顺序

1. 先搜索本站文档，确认问题是否已经有结论或排错步骤。
2. 了解 [GitHub 社区](/docs/community/github-community) 中不同入口的职责。
3. 如果结论不完整，在对应页面底部提交“有帮助”或“没帮助”反馈，并补充具体说明。
4. 如果需要持续跟踪，使用 [问题反馈](/docs/community/feedback) 说明情况；文档页反馈会由 GitHub Bot 创建 Issue。
5. 如果可以提供修复内容，按照 [参与共建](/docs/community/contributing) 修改源码并提交 Pull Request。
6. 如果是项目展示或资源互荐，再阅读 [友情链接](/docs/community/friend-links)。

## Pages 与 Bot 如何配合

主站使用 Fumadocs 导出到 GitHub Pages，不保存账号、对话、表单或审核状态。文档页底部的反馈由独立 GitHub App Bot 接收并创建 Issue，友情链接申请则进入仓库现有的 Issue / Actions / Pull Request 审核流程。Pages 承载公开页面，动态写入能力放在独立服务中按需运行。

这样可以把网站访问和协作写入分开：文档页面由 Pages/CDN 承载，只有用户主动提交反馈时才调用外部 Bot。Bot 不保存业务数据，GitHub App 私钥也不进入 Pages；维护者仍能在公开 Issue 和 PR 中查看上下文与变更原因。没有自有域名时，Bot 使用 `workers.dev` 地址即可。
