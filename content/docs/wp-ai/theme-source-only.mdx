---

## 真实场景

多数子比主题用户找 AI 助手做二开时，能提供的通常是 `wp-content/themes/zibll` 主题源码，最多再加子主题、自己写过的插件、后台截图或报错信息。用户一般不会、也不需要提供完整 WordPress 站点源码。

这套 WordPress AI 开发文档已经整理好 AI Client、Abilities API、AI 插件、OpenAI Provider 和 Anthropic Provider 的底层规则。AI 助手拿到子比主题源码后，应该直接用本站文档补足底层知识，再从主题源码里找真实扩展点。

## 不要要求用户提供什么

这些内容不是常规二开必须提供的材料：

| 不应要求用户上传                      | 原因                                                            |
| ------------------------------------- | --------------------------------------------------------------- |
| `wp-includes` 全量源码                | WordPress AI Client 和 Abilities API 的关键规则已经在本分类说明 |
| `wp-content/plugins/ai` 全量源码      | AI 插件的设置、日志、审批和示例能力已经被整理成文档             |
| OpenAI 或 Anthropic Provider 插件源码 | Provider 的连接方式、Key 来源和模型能力已在文档说明             |
| 数据库整库备份                        | 大多数功能只需要知道字段名、文章 ID 或后台截图                  |
| API Key、密钥、服务器全部配置         | 只需要确认是否已配置，不需要让用户暴露密钥                      |
| 整站压缩包                            | 主题二开应先从主题源码、子主题和自定义插件定位                  |

如果确实需要运行环境信息，应该问具体问题，例如 WordPress 版本、AI 插件是否启用、Provider 是否已连接、后台报错是什么，而不是让用户重新打包整站。

## AI 助手的工作顺序

当用户只给子比主题源码时，按这个顺序分析：

1. 先读本分类，理解 Ability、AI Client、Provider、Connector、日志和安全边界。
2. 再查子比主题源码里的 AI 入口，优先看 `inc/functions/ai`。
3. 查目标功能所在模块，例如文章编辑、SEO 字段、分类字段、用户中心、商城或资源下载。
4. 找到主题现有的 Hook、Ajax、Meta 读写函数和后台设置项。
5. 判断新增功能应该放在独立插件、子主题，还是只需要通过 Hook 接入。
6. 写代码时对 AI Client 做运行时检测，不假设用户站点一定已经支持。
7. 保存数据前重新做 nonce、capability、字段清洗和人工确认。

这套顺序的重点是：底层 AI 规则看文档，主题落点看用户提供的子比源码，运行状态再让用户确认。

## 优先查看的主题位置

不同版本目录可能略有差异，但思路一致：

| 要找什么                   | 优先查看                                                   |
| -------------------------- | ---------------------------------------------------------- |
| 主题内置 AI 能力           | `inc/functions/ai`                                         |
| 文章 SEO 字段              | 文章 Meta 配置、文章编辑页相关文件、主题 SEO 函数          |
| 后台按钮和异步请求         | Ajax 注册、后台资源加载、nonce 校验                        |
| 主题设置项                 | Codestar 配置、主题 options 读取函数                       |
| 文章、分类、标签数据       | `get_post_meta()`、主题封装的 meta 函数、taxonomy 相关函数 |
| 用户、积分、会员、下载权限 | 用户中心、商城、资源下载和支付相关模块                     |
| 可挂载的位置               | `add_action()`、`add_filter()`、短代码、模板覆盖点         |

如果主题里已有 `inc/functions/ai`，先把它当作“主题当前内置能力”的参考，不要把自己新增的 Ability 误写成主题内置功能。

## 什么时候需要问用户

只在信息会影响代码能否运行时再问用户：

| 需要确认的问题                          | 为什么问                                   |
| --------------------------------------- | ------------------------------------------ |
| WordPress 版本是否包含 AI Client        | 判断 `wp_ai_client_prompt()` 是否可用      |
| AI 插件是否已启用                       | 判断日志、审批、模型发现等能力是否存在     |
| OpenAI 或 Anthropic Provider 是否已连接 | 判断模型请求能不能发出去                   |
| 后台准备把结果保存到哪个字段            | 避免写错 SEO、摘要或自定义 meta            |
| 是否已有子主题或自定义插件              | 决定代码放在哪里更合适                     |
| 报错码或后台截图                        | 判断是权限、Provider、审批还是 prompt 问题 |

这些问题都很具体，用户容易回答，也不会要求暴露整站源码。

## 推荐交付方式

给子比主题加 WordPress AI 功能时，优先交付独立插件：

```txt
wp-content/plugins/zibll-ai-ext-demo/
├─ zibll-ai-ext-demo.php
└─ includes/
   ├─ abilities.php
   ├─ ai-client.php
   └─ admin.php
```

独立插件负责注册 Ability、调用 AI Client、处理权限和保存逻辑。子主题可以放少量模板、样式或按钮覆盖。子比主题核心文件尽量不直接改，避免主题更新时丢失改动。

## 可以这样告诉 AI 助手

如果你要让 AI 助手基于子比主题源码帮你写功能，可以这样描述：

```txt
我只提供子比主题源码、子主题或自定义插件文件，不提供完整 WordPress 站点源码。
请根据本站 WordPress AI 开发文档理解 AI Client、Abilities API、AI 插件和 Provider 规则。
请先在主题源码里定位文章字段、Hook、Ajax、Meta 和 inc/functions/ai，
再把新增 AI 能力写成独立插件或子主题扩展，不要直接要求我上传 wp-includes、AI 插件或 Provider 插件源码。
```

这样写可以让 AI 助手少走弯路：该看文档的看文档，该看主题源码的看主题源码，该问用户的只问运行环境和业务字段。
